# Backlog

Things we've decided to do later. One feature at a time: pick the one that matters most, build it small, check it on the phone.

## Next features we've talked about

- **Fatigue model from collected observations.** Use marked TS e1RM as the primary movement performance reference, working-set volume/reps/RPE, pre-session pattern soreness, and smoothed bodyweight trends. Flag sustained declines in context; suggest set/rep changes and, for persistent declines, a new block with a different movement. An exercise change needs its own performance baseline. No automatic prescription changes. Returning after long training lapses means subjective ratings must use absolute soreness levels, not an assumed "normal". The first provisional local-data trend model and manual recommendations are implemented (see Done). Next: review the observations on the phone, gather a baseline, and tune thresholds from real outcomes. Explicit pattern mapping for supplementary variants and tracking whether a suggested intervention was actually followed remain future work.

- **Parked: keep noisy sets out of the e1RM.** The e1RM is the highest e1RM across the sets, so one inflated set wins (the RPE table has to guess the reps left on a low-RPE set, e.g. an 8 @5 gives about 13 reps to failure). Decided 2026-10-08 to leave it until the e1RM is used to load weights; once the TS sets the TM it is only a metric. Preferred rule when it comes back: a set counts only if its RPE is 7 or higher (one constant in `exercise_state.py` and `log.html`; the last-set feature stays exempt). On the 19 Sep squat session that gives 332 (292 x 3 @8) instead of 343 (265 x 5 @6), the more trustworthy figure. Rejected: a rep cap (it would drop a real 9 @9.5 AMRAP) and a set-to-set window (it needs peer sets, so it can't judge a lone set, and a ramping session can mislead it). Bring it back if the e1RM tile looks too high.
- **Per-lift RPE charts you can edit and switch to.** The observed and estimated tables on `/rpe-charts` are read-only (see Done). Next: store a chart per lift (squat, bench, deadlift; every other movement keeps the General table), starting as a copy of the table in use, and a setting per lift for which chart it uses (the table in use stays the default), so an accepted table can start planning that lift's weights. Nothing changes silently: the user accepts a lift's table. Decided 2026-10-15; one feature at a time.
- **Refine the table fit.** The curve is steeper near the top (RTS article: https://store.reactivetrainingsystems.com/blogs/advanced-concepts/customizing-your-rpe-chart; their example loses 5 points per rep from 1 to 4 reps, 3.75 from 4 to 8, about half that beyond), so try a two-segment fit with a knot near 4 reps once there is data across it. And an optional real tested max per lift (a meet or gym 1RM) as the one pin that is not an RPE judgement. The gate constants (`MIN_SETS`, `MIN_WORKOUTS`, `MIN_K_SPAN` in `rpe_observed.py`) can be tuned once there is real data.
- **Use the exact RPE where the app reads Hevy history.** Hevy has no RPE below 6 or 6.5, so the Previous column, the last-session e1RM and the Progress page miss those sets. Overlay the RPE from `logged_sets` (matched by Hevy workout id and set position) onto Hevy history. Only works for workouts logged since 2026-10-15.
- **A way to clear a movement's TS.** Once a movement has a saved TS its e1RM is pinned to it (decided 2026-10-16), and there is no way back to the best-set e1RM short of clearing `training_max_history`.
- **The marked TS sets the TM at once.** Today a TS only sets the TM when the workout is saved, so a 1@8 done first doesn't change that session's planned weights (the e1RM basis does follow it). Make the TM tile use today's marked TS straight away.
